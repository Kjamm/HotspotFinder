# HotspotFinder v2 — 제품 설계 및 요구사항

작성·수정일: 2026-11-17 (Asia/Seoul)  
상태 — 로컬 앱 0.1 구현. EvoEF 자동 설치와 macOS arm64 실제 계산 검증 완료. FoldX·BudeAlaScan·Flex ddG는 연동 코드와 파서가 구현되어 있으며 실제 엔진 검증은 남아 있다. 현재 제공 기능과 실행 방법은 README에 정리했다.

## 1. 제품 목표와 범위

**복합체 PDB 한 개와 분석할 결합 파트너를 지정하면, 개인 컴퓨터에서 계면 잔기의 alanine scanning을 여러 예측 도구로 실행하고 hotspot 후보와 도구 간 일치·불일치를 한 화면에서 확인한다.**

사용자가 해결하려는 문제는 도구마다 다른 실행 방식, 잔기 표기, 결과 형식을 직접 맞추고 분석해야 한다는 점이다. 제품은 입력 준비, 실행 관리, 결과 해석, 근거 추적을 통합한다.

확정된 요구는 PDB 입력, 개인 컴퓨터에서 실행 가능한 도구의 계산 통합, 보기 쉬운 결과 제공, 여러 운영체제 지원이다. 기본 분석 도구는 FoldX와 EvoEF, 선택적 비교 도구는 BudeAlaScan, 사용자가 선택한 후보의 후속 분석 도구는 Flex ddG로 정한다. mCSM-PPI2는 지원 범위에서 제외한다.

첫 버전은 단일 사용자용 로컬 웹 애플리케이션이다. 원격 계산 API, 외부 서버로의 PDB 제출, 연구실 서버 운영, 다중 사용자 관리 및 HPC 연계는 포함하지 않는다. 설치와 필요한 파일 준비가 끝난 뒤에는 네트워크 없이 PDB 처리·계산·시각화·결과 저장을 수행한다. 이하 과학적 cutoff와 판정 임계값 중 “제안”으로 표시한 항목은 검증할 시작 설정이며, 성능이 검증된 수치라는 뜻은 아니다.

### 주요 연구 질문

- 어떤 잔기를 alanine으로 바꾸면 선택한 파트너와의 결합이 크게 약화되는가?
- 여러 도구가 같은 잔기를 중요하다고 예측하는가? 서로 다른 예측은 무엇인가?
- 후보가 원래 단백질의 어느 서열 구간과 3D 계면에 위치하는가?
- 각 판단에 사용된 구조, 변이, 계산 조건과 원시 결과는 무엇인가?

여기서 hotspot은 **지정한 구조·결합 파트너·변이·판정 기준에서 얻은 예측 후보**다. 계면에 가까운 잔기가 모두 hotspot은 아니며, 예측값은 실험적 결합 기여도의 확정값이 아니다. 첫 버전은 후보 우선순위 결정까지 다룬다. 새로운 펩타이드 서열 생성, docking, MD, 실험 효능 예측은 별도 확장 범위다.

## 2. 사용자 흐름

1. **구조 업로드:** PDB를 읽고 모델, 체인, 서열, 비표준 잔기, 좌표 누락 정보를 표시한다.
2. **계면 선택:** 결합 파트너 그룹 1과 그룹 2를 지정한다. 예: `A` 대 `B`, 또는 `AB` 대 `CD`. 변이를 넣을 쪽을 별도로 선택한다.
3. **후보 확인:** 거리 기반 계면 잔기를 보여주고, alanine 변이 목록을 만든다. 사용자는 후보를 추가하거나 제외할 수 있다.
4. **기본 계산 설정:** FoldX와 EvoEF의 설치 상태를 확인하고 반복 수와 프로토콜을 고른다. BudeAlaScan은 사용자가 추가로 선택할 수 있다. 미설치·미검증 도구는 설정 필요 상태로 표시한다.
5. **계면 분석:** 선택한 도구로 전체 후보를 계산하고 진행 상황과 부분 결과를 표시한다. 오래 걸리는 계산 중에도 화면을 사용할 수 있다.
6. **선택 후보 후속 분석:** 기본 결과에서 사용자가 명시적으로 고른 잔기에 Flex ddG를 실행한다. 기본 전체 스캔에 Flex ddG를 자동 포함하지 않는다.
7. **비교·내보내기:** 잔기별 표, 도구별 heatmap, 서열과 3D 구조를 연동해 보고 CSV 및 재현용 파일을 내려받는다. 기본 분석과 선택 후보 후속 분석의 대상·완료 상태를 구분한다.

PDB만으로 사용자가 의도한 PPI를 항상 결정할 수는 없다. 체인이 여러 개라면 선택한 파트너 조합을 명시해야 한다. 업로드 구조가 asymmetric unit인지 biological assembly인지 기록하며, 첫 버전은 제공된 좌표를 대상으로 하고 assembly를 임의 생성하지 않는다.

펩타이드 저해제 설계에서는 **원래 결합 파트너에서 보존하려는 잔기**와 **표적 단백질에서 접촉하려는 잔기**가 다르다. 분석 체인의 역할을 표시하고 양쪽을 분석한 경우 순위를 분리한다. hotspot들의 서열 연속성과 공간적 인접성은 함께 보여주되, 곧바로 독립적인 결합 펩타이드로 간주하지 않는다.

## 3. 과학적 계산 규약

### 3.1 계산 대상

기본 분석은 계면 후보의 단일 alanine 치환이다. 화면에서는 모호한 “잔기 친화도” 대신 **변이에 따른 결합 변화 예측**을 사용한다.

통일된 해석 방향은 다음과 같다.

`ΔΔG_binding = ΔG_binding(mutant) − ΔG_binding(wild type)`

- 양수: 변이에 의해 결합이 불리해짐. alanine 치환이라면 원래 잔기의 기여를 시사한다.
- 음수: 변이에 의해 결합이 유리해짐.
- 0 부근: 해당 방법에서 예측된 변화가 작음.

부호 통일은 방법 간 수치의 동등성이나 정확도를 보장하지 않는다. 원래 점수와 변환된 점수를 모두 보존한다.

### 3.2 도구별 통합 기준

| 도구·역할 | 확인한 기능과 연결 방식 | 결과 처리 | 구현 전 확인 사항 |
| --- | --- | --- | --- |
| FoldX · 기본 | 로컬 실행 파일로 구조 수선, 변이 생성, 파트너 간 상호작용 에너지 계산 | 대응하는 mutant와 WT의 binding energy 차이; kcal/mol | 사용할 버전, 실행 파일, 파라미터 파일, 실제 출력 형식 |
| EvoEF · 기본·추가 | 로컬 소스 빌드 후 구조 수선, 변이 생성, 파트너 간 binding score 계산 | mutant와 WT의 ComputeBinding 차이; 원시 점수와 단위 근거 보존 | 소스 revision, 빌드 환경, 라이브러리, 파트너 분할 및 출력 형식 |
| BudeAlaScan · 선택·추가 | 로컬 컨테이너에서 PPI alanine scanning 명령행 엔진 실행 | 출력의 부호·단위를 검증한 parser로 변환; 원시값 보존 | 컨테이너 이미지·CPU 구조, Python/SCWRL 등 의존성, 실제 출력 형식 |
| Flex ddG · 선택 후보 후속 분석 | 로컬 RosettaScripts 프로토콜로 구조 ensemble을 생성하고 변이 영향을 계산 | raw 점수와 보정 점수를 분리; 단위와 score function 보존 | Rosetta 버전, XML 프로토콜, 반복 설정, 분석 스크립트 버전 |

FoldX `BuildModel`은 변이별 대응 WT 구조를 만들며, 일반 출력의 총 에너지는 접힘 안정성이다. 따라서 그 값을 그대로 binding ΔΔG로 사용하지 않는다. 실행 경로는 `RepairPDB → BuildModel → 대응 WT 및 mutant 각각 AnalyseComplex → 차이 계산`으로 정한다. 각 반복의 대응 구조끼리 먼저 차이를 계산한 뒤 집계한다. [FoldX BuildModel](https://foldxsuite.crg.eu/command/BuildModel), [FoldX AnalyseComplex](https://foldxsuite.crg.es/command/AnalyseComplex)

EvoEF는 `RepairStructure → BuildMutant → WT 및 mutant 각각 ComputeBinding → mutant − WT` 순서로 연결한다. 선택한 파트너 그룹을 `--split`에 반영하며, 모든 체인 쌍의 결과를 선택한 계면의 값으로 오인하지 않는다. 공식 저장소는 로컬 빌드와 binding ΔΔG 계산을 설명한다. 단백질 이외 분자에 대한 제한을 capability에 반영하고, 보조인자를 묵시적으로 삭제하지 않는다. [EvoEF 공식 저장소](https://github.com/tommyhuangthu/EvoEF)

BudeAlaScan은 PPI alanine scanning용 로컬 명령행 엔진이다. BAlaS 웹사이트를 호출하거나 웹 서비스를 통째로 통합하지 않고, 계산 엔진만 adapter에 연결한다. 기존 standalone 컨테이너 정의에는 오래된 Python과 SCWRL 의존성이 있으므로 별도 환경에 격리하고 실제 예제로 검증한다. 원시 출력의 부호·단위를 확인한 뒤 변환 규칙을 고정하며, 검증 전에는 hotspot 판정에 사용하지 않는다. [BudeAlaScan 공식 저장소](https://github.com/richardbsessions/BudeAlaScan), [BAlaS standalone 컨테이너](https://github.com/wells-wood-research/BAlaS/blob/master/StandaloneAlaScanDockerfile)

Flex ddG는 backbone sampling을 포함하며, 공식 튜토리얼은 일반 분석에서 35회 이상 반복과 각 35,000 backrub steps를 안내한다. 이는 검토할 연구용 preset의 출발점이며 모든 구조의 정확도를 보장하는 기본값은 아니다. 축소된 시험 실행은 “연동 확인용”으로 구별하고 연구용 결과와 합치지 않는다. [Flex ddG 공식 튜토리얼](https://github.com/Kortemme-Lab/flex_ddG_tutorial)

Rosetta의 raw energy는 REU이며 프로토콜 간에도 직접 비교가 어려울 수 있다. 검증된 해당 프로토콜의 변환이 없는 값에 kcal/mol을 붙이지 않는다. GAM 등의 보정 결과도 변환식·학습 출처·적용 가능한 score function을 기록하고, 물리 단위가 확인되지 않으면 별도 척도로 표시한다. 다른 Rosetta 방법의 환산 계수를 가져와 적용하지 않는다. [Rosetta 단위 문서](https://docs.rosettacommons.org/docs/latest/rosetta_basics/Units-in-Rosetta)

**제외한 도구:** mCSM-PPI2는 확인한 공식 제공 방식이 웹 서비스이고 독립적인 로컬 실행 패키지를 확인하지 못했으므로 첫 버전에서 제외한다. 이는 로컬 버전이 존재하지 않는다고 단정하는 뜻은 아니다. 원격 API로 대체하지 않는다. [mCSM-PPI2 공식 도움말](https://biosig.lab.uq.edu.au/mcsm_ppi2/help)

EvoEF2도 로컬 실행이 가능하지만 이번 버전에는 추가하지 않는다. 개발자가 설명한 최적화 목적상 EvoEF는 ΔΔG 예측, EvoEF2는 서열 설계에 초점을 두므로 현재 목적에는 EvoEF를 우선한다. 모든 데이터에서 EvoEF가 더 정확하다는 뜻은 아니다. [EvoEF2 개발자 설명](https://github.com/tommyhuangthu/EvoEF2)

### 3.3 구조 및 잔기 식별

| 항목 | 제안 규칙 |
| --- | --- |
| 최초 지원 형식 | PDB; mmCIF는 후속 확장 |
| 모델 | 여러 MODEL이 있으면 한 모델을 선택; 다른 모델의 좌표를 혼합하지 않음 |
| 잔기 식별 | 구조 ID + 모델 + 체인 + PDB residue number + insertion code + 원래 잔기명 |
| 재번호 매김 | 도구가 요구할 때만 수행; 원래 번호와 도구 번호의 양방향 매핑 보존 |
| 대체 위치 | residue conformer 단위의 일관된 선택 정책과 occupancy를 기록; 모호한 경우 선택 요구 |
| 결손 | missing side-chain atom, missing backbone 및 서열 gap 구별; 자동 수선 여부 기록 |
| 비표준 잔기·보조인자 | 탐지 후 엔진별 지원 확인; 무조건 삭제하거나 표준 잔기로 바꾸지 않음 |
| 수소·물·이온 | 엔진별 전처리 정책과 유지·제거 항목을 기록 |
| 구조 보존 | 업로드 원본, 공통 선택 구조, 엔진별 전처리 구조를 별도 보존하고 해시 기록 |

다른 도구의 전처리 구조를 완전히 같게 만들 수 없는 경우, 그 차이를 분석 메타데이터에 남긴다. 변이 전후 또는 전처리 전후 잔기 매핑이 불명확하면 해당 작업을 중단한다.

### 3.4 계면과 변이 선정

- 계면 후보 기본값 제안: 두 파트너 그룹 사이 **중원자 최소 거리 ≤ 5.0 Å**. 사용자가 조정할 수 있게 하며, 이는 편의상 정한 기하학적 후보 기준이다.
- 계면 선정은 원본에서 모델·conformer·파트너 선택을 반영한 공통 구조를 기준으로 한다. 엔진별 전처리 후 접촉 변화도 추적한다.
- 선택한 그룹 사이의 접촉만 판정한다. 그룹 내부 접촉으로 계면 후보를 늘리지 않는다.
- Ala→Ala는 계산 대상에서 제외하고 “원래 alanine”으로 표시한다. 이를 ΔΔG=0 측정값으로 만들지 않는다.
- Gly→Ala는 측쇄 제거와 성격이 다르므로 기본 자동 후보에서 제외하고 선택적으로 포함한다. Pro 및 disulfide 참여 Cys는 구조 변화 가능성을 표시한다.
- 지원하지 않는 잔기·삽입 코드·체인 표기는 명시적으로 차단하거나 검증된 매핑을 사용한다.
- 사용자가 추가한 계면 밖 잔기는 수동 지정 후보로 구분한다.

## 4. 결과 통합과 hotspot 판정

### 4.1 공통 결과 레코드

| 표시 점수 | 결합 약화가 양수인 값, 단위, 변환 규칙·버전 |
| 반복 결과 | 계획·완료·실패 반복 수, 반복별 값, 평균, 표준편차 |
| 상태 | 성공, 실패, 미실행, 미지원, 취소, 계산 중 및 사유 |
| 검증 정보 | 입력·출력 파일 해시, 원시 결과 경로, 구조·매핑 경고 |

집계 키에는 구조·파트너·변이·프로토콜 맥락이 포함되어야 한다. 체인 `A:100`과 `B:100`, `100`과 `100A`, WT가 다른 변이는 합치지 않는다. NaN, infinity, 파싱 실패와 누락은 숫자 0으로 바꾸지 않는다. 반복이 하나면 표준편차는 0 대신 “산출 불가”로 표시한다.

### 4.2 합의 판단 제안

첫 버전의 기본 출력은 **도구별 값 + 판정 근거 + 분석 커버리지**다. 성격이 다른 값의 단순 평균으로 “통합 ΔΔG”를 만들지 않는다.

1. 각 도구의 승인된 프로토콜마다 hotspot 판정 임계값과 검증 근거를 저장한다. 검증된 기준이 없으면 점수·순위 비교만 제공하고 합의 판정에 포함하지 않는다. kcal/mol 결과에 2.0을 사용해 보는 것은 검증할 시작 설정의 예이며, 보편적으로 검증된 정답으로 취급하지 않는다. 원래 REU 값에는 kcal/mol 임계값을 적용하지 않는다.
2. 양수·음수 방향과 임계값 충족 여부를 별도로 보여준다. 음수 결과는 hotspot 지지가 아니다.
3. 합의는 같은 후보·구조·파트너 정의에 대해 판정 가능한 도구 중 지지 도구 수로 표시한다. 예: “지지 2 / 판정 가능 2 / 선택 3; 1개 실패”.
4. 초기 “합의 후보” 규칙은 판정 가능 도구가 최소 2개이고 그중 2/3 이상이 지지하는 것으로 제안한다. 임계값 미설정 도구는 판정 분모에서 제외하고 제외 사유를 표시한다.
5. 부분 결과에는 “잠정” 표시를 붙인다. 모든 선택 도구의 성공 여부와 별개로, 합의 계산에 실제 사용된 도구 목록을 저장한다.

도구별 상대 순위도 보조적으로 제공한다. 비교에는 모든 비교 도구에서 성공한 동일 후보 집합을 사용하고, 집합 크기와 동점 처리 규칙을 기록한다. 후보 수가 작거나 비교 가능한 집합이 없으면 통합 순위를 내지 않는다. 점수 합의는 독립적인 실험 증거의 개수나 정답 확률이 아니다.

Flex ddG의 raw 및 보정 점수는 같은 도구의 두 표현이므로 두 개의 독립적인 지지로 계산하지 않는다. 반복 간 표준편차는 계산 변동성이지 모델의 전체 예측 오차나 신뢰구간이 아니다.

Flex ddG를 선택하지 않은 잔기는 “후속 분석 미선택”으로 표시하고 0이나 실패로 취급하지 않는다. 기본 분석의 전체 후보 순위를 유지하고, 후속 결과가 있는 후보끼리의 비교를 별도로 제공한다. 추가 분석 후의 합의에는 잔기별 실제 참여 도구를 명시해, 일부 후보에만 추가 계산이 이루어진 것을 숨기지 않는다.

## 5. 로컬 실행 구조

**단일 사용자용 로컬 웹 UI, 분석 API, 계산 worker, 엔진 adapter, 결과 저장소를 분리한다.** 계산 프로세스는 HTTP 요청 수명과 독립적으로 실행한다. 웹 UI/API는 loopback 주소에서만 제공하며 외부 서버 없이 동작한다.

| 구성 요소 | 책임 | 채택 구성 |
| --- | --- | --- |
| 웹 UI | 입력, 작업 관찰, 표·서열·구조 연동 | React + TypeScript, Mol* |
| 분석 API | 입력 검증, 분석 명세 고정, 결과 제공 | Python + FastAPI |
| 구조 처리 | PDB 파싱, 잔기 매핑, 공간 접촉 검색 | Biopython Bio.PDB |
| 작업 관리자 | 대기열, 자원 제한, 재시도, 취소, 재시작 복구 | 독립 worker 프로세스와 영속 작업 테이블 |
| 엔진 adapter | 입력 작성, 로컬 실행, 상태 조회, 출력 파싱, 정규화 | 엔진별 독립 Python 모듈 |
| 저장소 | 분석·결과 메타데이터 및 원시 파일 | SQLite + 로컬 작업 디렉터리 |

위 구성으로 구현하며 구체적 패키지 버전은 설치 검증 단계에서 고정한다. 구조 시각화·파싱·API 도구의 역할은 공식 문서에서 확인했다. [Mol*](https://molstar.org/), [Bio.PDB](https://biopython.org/docs/latest/api/Bio.PDB.html), [FastAPI](https://fastapi.tiangolo.com/)

### 지원 환경 및 설치 검증

| 환경 | 실행 경로 | 활성화 조건 |
| --- | --- | --- |
| macOS · Apple Silicon 및 Intel | FoldX/EvoEF/Flex ddG는 호환되는 로컬 실행 파일 우선; BudeAlaScan은 로컬 컨테이너 | 해당 OS·CPU·실행 방식 조합에서 실제 예제 계산과 파싱 통과 |
| Linux | 로컬 실행 파일; BudeAlaScan은 로컬 컨테이너 | 해당 OS·CPU 조합의 예제 검증 통과 |
| Windows | WSL2 내부에서 API·worker·엔진을 실행하고 Windows 브라우저로 접속; BudeAlaScan은 로컬 컨테이너 | WSL2 경로·파일 접근·브라우저 연결 및 실제 예제 검증 통과 |

이는 지원 대상이며 현재 지원을 검증했다는 뜻은 아니다. 특히 Apple Silicon의 실행 파일·컨테이너 CPU 구조를 확인한다. 에뮬레이션을 사용하는 경우 이를 실행 환경에 기록하고 그 조합을 별도로 시험한다. 호환성을 확인하지 않은 엔진을 사용할 수 있는 것으로 표시하지 않으며, 로컬에서 실패했다고 원격 서버로 전환하지 않는다.

GPU를 필수 조건으로 두지 않는다. 동시 계산 프로세스는 기본 1개이고 사용자가 자원에 맞춰 조정한다. 컨테이너 이미지, 엔진 라이브러리, 웹 UI의 JS·스타일·글꼴·시각화 자산을 설치 시 로컬에 준비한다. 분석 도중 CDN, 원격 구조 조회 또는 이미지 자동 다운로드에 의존하지 않는다.

엔진 설정에는 실행 파일 경로 또는 컨테이너 이미지 식별자, 엔진·프로토콜 버전, 의존 파일 경로, OS·CPU 및 실행 방식, 설치 검증 상태와 최근 시험 결과를 저장한다. 검증 상태는 `not_installed / needs_validation / ready / failed / unsupported`로 구분한다. 실행 파일·이미지·프로토콜·실행 환경이 변경되면 다시 검증하기 전까지 `ready`를 해제한다. 미설치 도구 때문에 나머지 도구의 실행을 막지는 않지만, 선택된 도구와 실제 실행 도구를 명시한다.

### Adapter 인터페이스

공통 계약은 `capabilities`, `validate`, `prepare`, `submit`, `poll`, `collect`, `normalize`, `cancel`로 유지한다. `submit`은 로컬 대기열에만 작업을 등록한다. 엔진 ID는 `foldx / evoef / budealascan / flex_ddg`로 정한다. `capabilities`는 지원 파트너 구성·잔기·입력 제한·실행 환경·검증 상태를 제공한다. 선택한 파트너 그룹을 정확히 표현할 수 없는 엔진은 해당 조건을 미지원으로 처리한다. 체인을 분리하거나 번호를 바꾸는 전처리는 매핑과 입력 변경 내역을 남긴다.

### 작업 관리 요구사항

- 작업 단위는 엔진 × 변이 × 반복이다. 필요하면 엔진 내부 batch로 묶되 결과는 개별 단위로 추적한다.
- 개별 상태는 `queued / running / succeeded / failed / cancelled / unsupported`; 전처리 단계도 표시한다. 선택하지 않은 작업은 별도 미실행 상태로 유지한다.
- 상위 분석은 `completed / partial / failed / cancelled`를 구분한다. 일부 성공을 전체 성공으로 표시하지 않는다.
- 실행 중 앱이 종료되면 작업 기록을 복구한다. 프로세스·컨테이너 식별자와 출력 상태를 확인한 뒤 중복 실행 없이 재개 또는 실패 처리한다. 완료된 계산은 보존한다.
- 계산 실패는 사유를 표시하고 사용자 재시도로 새 시도 기록을 만든다. 유효한 완료 결과를 덮어쓰거나 동일 작업을 중복 등록하지 않는다.
- 작업 디렉터리를 격리하고 사용자 파일명이나 입력을 shell 명령 문자열에 삽입하지 않는다.
- CPU·메모리·동시 실행 수·시간 제한을 설정한다. 동시 프로세스 기본값은 1개이며, 예상 시간은 해당 실행 환경의 실제 benchmark를 쌓은 뒤 제공한다.
- 캐시 키는 입력 및 전처리 해시, 파트너, 변이, 엔진·프로토콜 버전, 파라미터, seed를 포함한다.
- 취소는 하위 프로세스 또는 해당 작업의 컨테이너까지 전달한다. 이미 완료된 다른 작업의 결과는 유지한다.

### 출력과 재현성

최소 산출물은 요약 CSV, 전체 결과 JSON, 분석 명세 JSON, 잔기 매핑 CSV, 원본·전처리 PDB, 엔진 원시 출력과 로그다. 해시 목록과 사용한 소프트웨어·논문 출처를 함께 저장한다. 외부 CSV를 가져온 경우 계산 실행 결과와 구별하고, 구조·파트너·변이·단위가 확인되지 않으면 합의 계산에서 제외한다.

모든 구조·결과·로그는 로컬 작업 디렉터리에 저장하고 사용자가 삭제하기 전까지 보존한다. 외부 계산 서버로 PDB를 전송하는 기능은 제공하지 않는다. 내보내기와 기존 결과 파일 가져오기도 로컬 파일 작업으로 수행한다.

FoldX와 Rosetta는 설치·배포 방식 결정 시 해당 버전과 사용 목적의 라이선스를 확인한다. 현재 앱은 사용자가 받은 공식 배포 압축 파일을 선택하면 압축 해제, 실행 파일 탐색, 경로 저장, 시험 계산을 수행한다. 기존 설치는 고급 설정에서 연결할 수 있다. [FoldX 이용 안내](https://foldxsuite.crg.eu/licensing-and-services), [Rosetta 다운로드·라이선스 안내](https://rosettacommons.org/software/download/)

EvoEF 소스 및 BudeAlaScan과 그 의존 도구도 고정할 버전의 라이선스·배포 조건을 기록한다. BudeAlaScan 컨테이너에 필요한 별도 라이선스 의존 도구가 있으면 사용자가 준비한 설치 파일을 연결하며, 계산 엔진 저장소의 라이선스가 모든 의존 도구까지 포괄한다고 가정하지 않는다.

| 3. 선택 분석 및 비교 | BudeAlaScan 컨테이너, 선택 후보 Flex ddG, 합의·heatmap·3D·내보내기 | 기본/후속 분석 구분, 잔기 매핑 및 모든 표시·출력의 일치 |
| 4. 운영체제별 검증 | Mac·Linux·Windows/WSL2의 검증된 지원표와 설치 안내 | 지원한다고 표시하는 엔진·환경마다 실제 계산과 오프라인 사용 검증 |

**다중 도구의 실제 로컬 계산이 제품의 완료 조건이다.** FoldX/EvoEF 기본 분석, BudeAlaScan 선택 분석, 선택 후보 Flex ddG 및 결과 통합을 단계별로 검증한다. 외부 결과 import는 초기 파서 검증과 기존 분석 재활용의 보조 경로이며 계산 연동을 대체하지 않는다. 특정 OS·CPU에서 미검증 또는 실패한 엔진은 지원 미완료로 명시하고, 다른 환경의 성공을 그 조합의 성공으로 간주하지 않는다.

### 검증 요구사항

| 구분 | 수용 기준 |
| --- | --- |
| 부호·단위 | 엔진별 원시값 보존 및 부호 변환 검증; BudeAlaScan parser의 실제 출력 대조; REU·단위 미확인 점수와 kcal/mol 혼합 집계 차단 |
| 에너지 의미 | FoldX 접힘 에너지 파일을 binding ΔΔG로 가져오면 거부; FoldX 대응 WT·mutant 및 EvoEF ComputeBinding 차이 검증 |
| 식별자 | 같은 residue number의 다른 체인, insertion code, 음수 번호, 다중 모델 fixture를 정확히 구분 |
| 구조 검증 | 잘못된 PDB, 한쪽 파트너 누락, 모호한 매핑, 지원하지 않는 잔기는 실행 전에 구체적 오류 표시 |
| 계면 | 알려진 좌표 fixture에서 cutoff 경계와 그룹 간 거리 계산 확인; cutoff 변경에 따른 후보 이력 보존 |
| 변이 | 실제 WT와 요청 WT 불일치 차단; Ala→Ala 제외; 수동 후보와 자동 후보 구분 |
| 결측·부분 결과 | 실패·미지원·미실행을 0으로 표시하지 않음; 판정 기준 미검증 도구 제외; 지지 수·판정 가능 수·선택 수가 정확함 |
| 선택 후보 분석 | Flex ddG가 명시적으로 선택한 잔기에만 실행됨; 미선택은 실패와 구분; 전체 후보 순위와 후속 후보 비교가 분리됨 |
| Ensemble | 반복 수·seed·중간 checkpoint를 구분; 서로 다른 checkpoint를 독립 반복으로 합치지 않음 |
| 작업 복구 | 취소, 시간 초과, 중복 요청, 프로세스·컨테이너 종료 시 완료 결과 보존 및 중복 계산 방지 |
| 화면·내보내기 | 선택 잔기가 표·서열·3D에서 일치; CSV/JSON의 값·단위·상태가 화면과 일치 |
| 실제 엔진 | 설치된 승인 버전의 공식 예제로 end-to-end 실행; 동일 PDB·파트너·변이·설정의 직접 명령행 결과와 앱 결과가 parser 정밀도 내 일치 |
| 운영체제 | Mac CPU별, Linux, Windows/WSL2의 설치·입력 경로·실행·파싱 검증; 미검증 엔진을 활성화하지 않음 |
| 오프라인 | 설치·파일 준비 후 네트워크 차단 상태에서 계산·3D 시각화·열람·내보내기 완료; 숨은 CDN·원격 API 의존성 없음 |
| 자원 설정 | 기본 동시 프로세스 1개 준수; 사용자 지정 상한과 취소가 실제 프로세스·컨테이너에 반영됨 |
| 연구 성능 | 실험 ΔΔG가 있는 별도 평가 자료에서 방법별·합의별 성능을 측정하고 비교 |

과학적 검증에서는 개발/임계값 선택용 데이터와 평가용 데이터를 분리하고, 같은 복합체의 유사 변이가 양쪽에 섞이는 누출을 통제한다. 상관계수, 단위가 맞는 경우 오차, hotspot precision/recall, 미계산 비율을 함께 보고한다. 합의가 개별 방법보다 낫다는 가정은 평가 후 판단한다. 실행 성공률과 예측 정확도는 별도 지표로 관리한다.

## 7. 확정 사항과 구현 단계의 검증 항목

| 항목 | 확정한 설계 | 구현 단계의 검증 또는 입력 |
| --- | --- | --- |
| 실행 환경 | 단일 사용자 로컬 웹 UI·worker·SQLite; Mac/Linux/Windows 지원 대상, Windows는 WSL2 | OS·CPU·엔진 조합별 실제 실행 및 호환성 검증 |
| 계산 대상 | 계면의 단일 alanine scanning | 대표 protein–protein 및 protein–peptide 구조 fixture |
| 분석 체인 | 파트너 역할과 변이 대상 별도 선택 | 사용자가 각 분석에서 선택; 엔진의 파트너 표현 지원 확인 |
| 기본 엔진 | FoldX + EvoEF | 이용 가능한 실행 파일·소스 revision·라이브러리 및 직접 실행 대조 |
| 선택 엔진 | BudeAlaScan 추가 비교, 선택 잔기 Flex ddG 후속 분석 | 컨테이너 의존성 및 반복 계산 프로토콜 검증 |
| 자원·네트워크 | GPU 필수 아님; 동시 계산 기본 1개; 설치 후 오프라인 | CPU·메모리 요구량 benchmark, 네트워크 차단 시험 |
| 판정 기준 | 근거가 검증된 도구별 threshold만 합의에 사용; 나머지는 점수·순위 표시 | 분리된 평가 데이터에서 임계값·단위·성능 검증 |
| 기준 예제 | 엔진 공식 예제와 식별자·구조 경계 사례부터 검증 | 이후 사용자 대표 PDB 및 기존 결과로 연구 워크플로 확인 |

이 문서는 제품 요구사항을 기록한다. 2026-11-17 로컬 웹 앱을 구현하고 macOS arm64에서 EvoEF 설치·시험 계산 및 1JTG 두 잔기의 직접 실행 일치를 확인했다. FoldX·Rosetta 실행 파일과 Docker 환경이 준비되지 않아 해당 엔진의 실제 실행 검증은 남아 있다. 외부 결과 파일 가져오기는 후속 구현 항목이다. 최신 실행 및 검증 범위는 README를 따른다.
